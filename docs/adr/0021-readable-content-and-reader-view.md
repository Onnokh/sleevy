# Readable Content and the Reader View

Sleevy will extract the prose of an **Article** at enrichment time, store it per **Link** under the new term **Readable Content** — as the extractor's article HTML and as the Markdown converted from it — and render the Markdown in a new **Reader View** so a Saved Item can be read inside the product instead of only being handed to a browser. This supersedes three v1 decisions recorded in CONTEXT.md: that "a **Link** retains **Saved Metadata**, not the full original content", that "**Extracted Page Content** may be used during **Enrichment** but is not persisted in v1", and that "V1 has no Saved Item detail screen; list rows are the primary item surface". Each of those was right for a product whose only job was to remember a URL and say one sentence about it. A read-later app that never lets you read is the one thing the category is named after, so the Reader View is the surface those invariants were holding the place for.

**Readable Content is the article prose, not an archive.** Shiori — the closest prior art, and the design this follows — produces three artifacts from one save: a readable body, an optional WARC copy of the page with every asset, and an optional EPUB. Sleevy takes only the first. No assets are downloaded, no byte-exact copy is kept, and an **External Image URL** stays an external URL that clients load themselves, exactly as it does today. That boundary is what lets the retired invariant keep its meaning: a Link still does not retain the page, it retains what the page said. It also keeps the legal posture legible. Storing an article body is a heavier copyright position than storing a title and a two-sentence **Preview Summary**, and Sleevy accepts it on the same footing every reader mode does — content is extracted for one Account's own later reading, never republished, and specifically never served on a **Public Profile**, whose Saved Item shape is an allow-list (ADR 0016) and therefore excludes Readable Content by construction rather than by remembering to.

**Readable Content is stored in two forms, and only one of them is served.** Shiori keeps a plain-text `Content` column for search beside a sanitized `HTML` column for rendering, and returns both from `GET /api/v1/bookmarks/{id}/readable`. Sleevy keeps two forms as well, but a different pair and with a different contract: the extracted article **HTML** exactly as Readability produced it, and the **Markdown** converted from it. Markdown is what the **Reader View** renders and what search indexes, because it is safe by virtue of what it is rather than what strips it, it renders natively in SwiftUI and in the **Web Companion**, and it makes every article look the same, which is the whole point of a reader mode. The HTML is stored and not served. It exists because the conversion to Markdown is lossy and one-way — tables, figure captions, footnotes, and embedded players degrade or disappear — and re-fetching the page later to recover them is not a plan, since by then the page may be paywalled, rewritten, or gone. Keeping the extractor's own output means a better conversion can be run against every Link Sleevy has ever saved, without asking the network for anything. The consequence to state plainly: the day the Reader View renders that HTML instead of re-converting it, Sleevy needs an HTML sanitizer on both clients, because the markup is third-party and carries whatever script and tracking pixels survived extraction. That is a real cost, deliberately taken on later and not in this change; nothing in v1 serves the HTML column, so nothing in v1 needs the sanitizer.

**Extraction runs locally first and escalates to Cloudflare only where the cheap path already failed.** Mozilla Readability is the same algorithm Shiori uses through its Go port, it runs against the `linkedom` document Sleevy already builds for every fetched page, and it costs CPU rather than money or a network hop. So it is the default, converted from article HTML to Markdown. Cloudflare Browser Rendering's `/browser-rendering/markdown` endpoint is the fallback, reached with the account and token `CloudflareBrowserFetcher` is already configured with, and reusing the low-confidence signal `PageFetcher` computes today rather than inventing a second one — if a page was weak enough to need the browser for its title, it is weak enough to need it for its body. That call passes `html` rather than `url` whenever Sleevy already holds the markup, which is the difference between paying for a conversion and paying for a second browser navigation; on the Workers free plan, where quick actions are limited to one request per ten seconds, that distinction decides whether an enrichment queue moves at all. Making Cloudflare the primary extractor was considered and rejected on exactly that arithmetic: it would put a metered, rate-limited, externally-owned dependency on the critical path of every single capture, to improve an extraction that Readability already gets right on the ordinary article.

**The extraction gate and the parse are two passes over the DOM, and only the gate decides.** Readability exposes a cheap check before the expensive parse. Shiori calls both: `readability.Check` scores the page, `readability.FromReader` extracts it, and the check's verdict is applied afterwards. That ordering has a trap worth copying the shape of but not the details — when the check says no, Shiori clears `Content` but leaves `HTML` populated, so a bookmark reports `HasContent = false` while its readable endpoint still returns markup. Sleevy takes the simpler rule: one gate, one artifact. If the check rejects the page, no **Readable Content** is written at all. Sleevy also avoids the cost Shiori pays to run both passes. Because Go's readability consumes an `io.Reader`, Shiori holds the page body three times in memory at once — one buffer for the archival copy, one for the check, one for the parse — while the JavaScript port takes a parsed document, which Sleevy already builds with `linkedom` for every fetched page. So the check runs against a document, not a stream. The parse then needs a second, fresh document, because Readability mutates the tree it is given; `extractPageContent` already documents that same hazard, and the **Enrichment Job** already re-parses per consumer, so this adds a parse rather than a new rule. Two thresholds come from the library and are worth stating rather than discovering: a page yields nothing below roughly 500 characters of article text, and the gate wants a single block of at least 140 characters before it scores anything at all. The node-count limit that both ports leave uncapped by default is set here, because Sleevy runs this against URLs anyone can submit.

**Readable Content is its own table, its own request, and a flag that is neither.** It lands in a new one-to-one `link_content` record beside `link_metadata` and `link_enrichment`, extending the split those two already record — fetched page data and generated classification evolve independently, and a stored body is a third thing that evolves on its own schedule again. Shiori is the argument for this rather than against it, because it did the opposite and then had to work around it: its Postgres `bookmark` table carries `content` and `html` inline, so every list query hand-assembles its column list to leave them out and appends them only when a caller asks, and the "does this have a body" answer is a computed `content <> ''` bolted onto the same select. Its SQLite backend, which came later, keeps content in a separate `bookmark_content` table instead and denormalizes a `has_content` boolean back onto the row — the same conclusion reached the long way. Sleevy starts there, and storing two forms rather than one makes the separation matter more, not less. `link_content` holds one row per **Link**, keyed the same way `link_metadata` and `link_enrichment` are, with the article HTML and the Markdown as two columns on that row rather than two rows or two tables: they share a key, a lifecycle, and a writing transaction, so splitting them would be one record kept in two places. Postgres moves large text values out of the main heap on its own, so a read that does not name the HTML column does not pay for it, and the Reader View's query names only the Markdown — which is the discipline Shiori has to apply by hand, assembling column lists per query because its body columns sit on the row every list already reads. A boolean on `link_enrichment` records whether extraction produced anything, and that flag is what a Saved Item response carries, so a list read answers "is there a Reader View" without joining the body table at all. The Reader View then fetches the Markdown from a dedicated endpoint that never returns the HTML column. Each form is capped independently — Shiori sets no ceiling at all and leans on the database, but article HTML routinely runs several times the size of the Markdown it converts to, so the pair is where a pathological page turns into a storage incident soonest.

**Search indexes the Markdown and nothing else.** Shiori's two backends diverge here in a way that is instructive twice over. Its SQLite backend searches through an FTS5 virtual table declared over `title, content, html` — which indexes the markup, so tag and attribute names are searchable terms and a query for a word that happens to be an HTML element can match a page that never used it. Its Postgres backend, the one Sleevy shares, has no index at all and falls back to `content LIKE '%keyword%'`, an unindexed sequential scan over a text column. Neither is a model. So `link_content` is created with a generated `tsvector` over the Markdown column only, with a GIN index, from the start; the HTML column is never indexed. Neither the **Search Tab** nor the **Command Palette** reads it in this change. Adding the column later means rewriting the whole table; changing the query later is free, and it keeps a decision about search ranking — whether matching an article's body should rank beside matching its title is a product question, not a schema one — out of a change that is about reading.

**Extraction is a best-effort Enrichment stage, and the Reader View is never a dead end.** It runs inside the existing **Enrichment Job** as one more stage that skips rather than fails, the way **Extracted Page Content** does now, so a Link that yields no prose is exactly as usable as it is today. Readability's own check gates it, which also handles **Type** for free: a Video, a Repository, or a Post is not an article and produces nothing, and no rule about types has to be written to say so. Extracted Page Content survives as a separate term and keeps its job — it is the ~2000-character slice sent to **AI Enrichment**, now taken from the head of the Readable Content when there is any, and from the existing heuristic when there is not. Opening a Saved Item that has Readable Content opens the Reader View and marks it read through the same **Open Action**; opening one that has none sends the user to the Original URL in the browser, as it always has. So the Reader View is an upgrade on a path that already works, and no client needs to know in advance which it will get.

Deferred on purpose: re-extraction of already-saved Links (Shiori exposes this as `PUT /api/v1/bookmarks/cache`; Sleevy's Readable Content is written once per Link and a backfill is a later operational concern), offline availability of the body on iOS, EPUB export, and any archive of the page itself.

**Amended during Slice 1: Cloudflare supplies markup, never Markdown.** This ADR named `/browser-rendering/markdown` as the extraction fallback. Tested against real pages, that endpoint converts a whole document — it emits a YAML frontmatter block and keeps the navigation, because it is an HTML-to-Markdown converter and not an article extractor; Cloudflare's own parameter list offers no main-content option. Its output is a copy of the page, which is the one thing Readable Content is defined not to be. The escalation is therefore withdrawn, and with it the nullable HTML column it would have required: both stored forms are always present again.

Cloudflare remains load-bearing, one layer up. Sleevy's origin is a Hetzner host whose addresses many sites refuse outright, so a plain fetch returns 403 for pages that are perfectly ordinary articles. `PageFetcher`'s existing Cloudflare tier already answers that: it renders the page and returns markup, and extraction then runs against that document like any other. Two links that a direct fetch could not reach at all were measured end to end through that path and yielded 8,393 and 6,198 characters of clean article Markdown. So the division is that Cloudflare gets the page and Readability decides what an article is — one gate, one extractor, whatever the markup cost to obtain.

A second escalation, re-rendering a page that fetched cleanly but that Readability could not structure, was built and then removed. Across nineteen candidate pages it recovered one, and that one was a validator tool's own UI rather than an article. That sample is a developer's bookmarks read from a residential address and is not representative, so this is recorded as unproven rather than disproven: the measurement to make first is the extraction rate from the production host, where the blocked-fetch rate is higher and the arithmetic may differ.

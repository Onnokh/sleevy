# The Unread Widget Reads the App-Published Backlog, Not the API

The Native iOS App gets a second Home Screen widget, the **Unread Widget**: the size of the **Unread Backlog** and its newest **Saved Items**, with a tap on a row opening that item. The first widget, Reading Activity, calls a **Public Profile Endpoint** directly: that endpoint needs no credential, so the widget fetches for itself and only borrows the Handle from the app group. The Unread Backlog is private. A widget that fetched it would need the **App Session** token, and that token rotates on every response through the `set-auth-token` header. A rotation the widget received and the app did not, or the reverse, signs the reader out on one side; making both processes write the same keychain entry from concurrent timelines is the kind of race that takes a week to reproduce. The widget also has a memory and time budget that a list fetch plus favicon loads would spend on every reload.

**The app publishes, the widget reads.** Each time `ReadingListStore` projects a new Inbox snapshot with known coverage (cached, complete, or stale — never loading or failed, whose empty item lists say nothing about what is unread), or the Folder list changes, it writes an **Unread Backlog Snapshot** to the app group: for the whole Inbox and for each **Folder**, the count and the newest eight items as title, host, favicon URL, and save time; the Folder list itself; and the publish time. The widget takes one setting, the scope: the whole Inbox, the **Library**, or one Folder, so a reader can pin a Folder's unread share or the whole collection next to the Inbox. The Library scope is the one place the widget shows read items: the newest Saved Items regardless of Read State, with the Unread Dot on the unread ones and the total number of saves as its count, published from the same index state as the Inbox and wearing the same aurora, since both are the whole collection and only the caption tells them apart. The configuration sheet lists Folders from the same snapshot rather than asking the API. It then asks WidgetKit to reload the widget. Sign-out clears the snapshot and reloads again, so a signed-out device shows no previous reader's Inbox. The widget's timeline provider reads that snapshot, fetches and downsamples the favicons once into an app-group cache, and emits the same state at several later dates so the recency labels keep counting between publishes. The widget therefore holds no credential, calls no Sleevy endpoint, and can never rotate a token. The cost is freshness: an item captured from the Chrome Extension or Raycast while the phone is in a pocket reaches the widget only when the app next syncs, in the foreground or on the next launch. That is the trade the first widget avoided by being public, and it is the right one here: a stale count is a nuisance, a signed-out reader is a bug report. If a background refresh path is wanted later, it belongs in the app, which already owns the token, not in the widget.

Taps on the count panel travel as `sleevy://` URLs, a scheme added to the app for this purpose: `sleevy://inbox` selects the Home Tab, `sleevy://library` the Library Tab, and `sleevy://folders/{id}` opens that **Folder View** in the Library Tab. The app also answers `sleevy://saved-items/{id}` by running the **Open Action** for that item, but the widget rows do not use it: routing a row through the app brought the app to the front for a moment before Safari opened. A row is instead an interactive widget button running an App Intent inside the widget extension. The intent appends the read to the shared read-state queue, which moved to `Shared/` for this purpose and which the app already drains on its next sync exactly as it drains reads made offline; rewrites the published snapshot without the row so the widget updates at once; and returns an `OpenURLIntent`, so the link opens directly. The trade is that the server, and with it the Web Companion and other devices, learn about the read on the app's next sync rather than at the tap. The Open Action's own analytics are not recorded for these reads; the drain sends a plain read-state change.
